Part 1: Meet the Open-Meteo API + Browser Demo

Look First — A Real Request and a Real Response

Stop. This is the moment the last two sessions have been building toward. Here is a complete, real API request — and you can already read every piece of it from Session 2:

https://api.open-meteo.com/v1/forecast?latitude=35.28&longitude=-120.66&current=temperature_2m&temperature_unit=fahrenheit

Before you run anything, inspect the URL: identify the endpoint, location, requested variable, and units. Then select Copy URL, paste it into a browser, and press Enter. The result is raw JSON.

ImportantInvestigate Before You Run

Predict what the server will return from the URL alone. Only then press Run in R. Keep the R console visible so everyone can see the request, status, and response.

{
  "latitude": 35.28,
  "longitude": -120.66,
  "timezone": "GMT",
  "current_units": { "time": "iso8601", "temperature_2m": "°F" },
  "current": {
    "time": "2026-08-06T16:00",
    "temperature_2m": 71.4
  }
}

Now in Words

For a day and a half, “request” and “response” have been arrows on a diagram. They just became real — and you did not write a single line of code. That was the payoff of Session 2’s URL anatomy: a request is just a URL — so a web browser can make one. Reading the URL piece by piece:

  • https://api.open-meteo.com/v1/forecast — the endpoint (the stable front door)
  • ? — “here come my details”
  • latitude=35.28&longitude=-120.66 — where (San Luis Obispo)
  • current=temperature_2m — what (the temperature right now)
  • temperature_unit=fahrenheit — how (in °F)

And every piece of the response is something you already know:

  • The endpoint and the query string in the address bar (?, &, key-value pairs) — Session 2
  • The response wrapped in curly braces { } — the body, in JSON — Session 1
  • Data (temperature_2m: 71.4) and metadata (current_units, timezone) — Session 1
  • Your browser made a GET request — typing a URL into the address bar is always a GET — Session 2

That number — 71.4 — is the actual temperature in San Luis Obispo right now. A server you’ve never seen just measured the world and handed you the answer, because you asked correctly.

Change the coordinates to Boston (42.36, -71.06) and reload. Ask: How does its weather compare with San Luis Obispo? This is the question we will answer across cities and dates.

About This API

We will use Open-Meteo for the rest of the workshop — a free weather API built for exactly this kind of learning:

  • No sign-up. No API key. No credit card. You can start making requests immediately.
  • The main endpoint is https://api.open-meteo.com/v1/forecast — the endpoint from Session 2: the stable “front door” that never changes. Everything else we want (which city, which measurements, which units) goes in the query string.
NoteWhy api.open-meteo.com and Not Just open-meteo.com?

Notice the endpoint is not the same address as the regular website. Open-Meteo actually has two front doors:

  • open-meteo.com — the door for humans: a web page with documentation, meant to be read in a browser.
  • api.open-meteo.com — the door for programs: a server whose only job is to answer requests with raw JSON data.

Putting the API on its own api. subdomain is a near-universal convention — it lets the company run, scale, and update the data service separately from the marketing/docs website. When you see api. at the front of a domain, you’re looking at the machine door, not the human one. Keep this in mind: later today we’ll meet a third door for a different service.

NoteWhat About API Keys, Clients & Secrets?

Many commercial APIs (OpenWeather, X, Spotify, …) require you to register and receive credentials — an API key, sometimes a client ID and secret — which you attach to every request like an ID card, and which you must store carefully (never directly in your script!). It’s an important real-world concept, and the Practice Labs on this site show it in action.

But today we get to skip all of it. Open-Meteo is free and open — so we can spend our hour on the actual skill: requests and responses.

Important🎯 The Goal — Half Met Already

Read the goal sentence again: “Make a request to an API, then format the response into something we can analyze.”

  • Make a request to an API — ✅ you just did it. That URL was the request.
  • Get a response — ✅ you just did that too. That JSON was the response.

With zero lines of code, the request/response loop from Sessions 1 and 2 just happened for real, on your screen. So what’s left for R? Automation. The browser can make one request at a time, by hand, and you have to read the JSON with your eyes. R will do exactly the same thing the browser just did — same URL, same GET, same JSON — but it can do it a hundred times in a loop and hand the answers back as data you can analyze. That’s the entire rest of the workshop: not a new idea, just automating the thing you just did.

Part 2: The ETV Cycle + Extract in R

Look First — The Map for the Rest of the Workshop

Everything we do from here on follows one repeating cycle — ETV:

Step Name What it means In code
E Extract Make the request, receive the JSON response request() → req_url_query() → req_perform()
T Transform Format the response into a data frame resp_body_json() → tibble()
V Visualize Turn the data frame into a plot ggplot()

Now in Words

We’ll do E and T in this session and add V in Session 4. Whenever you feel lost in code, ask: which ETV step am I on right now?

Load Libraries

Each library we load is hired for one specific ETV job. Read the comments as a map of the whole workshop:

library(httr2)       # E: makes web requests
library(tibble)      # T: tidyverse data frames
library(dplyr)       # T: data manipulation
library(purrr)       # T: map() — apply a recipe to many inputs
library(ggplot2)     # V: visualizations

The Functions Behind Each Letter

Here’s the deeper look — the specific functions each library gives us, and exactly where they sit in the cycle:

Library Key functions ETV step What it actually does
httr2 request(), req_url_query(), req_perform() E request() starts from the endpoint, req_url_query() builds the query string (the part after ?), and req_perform() actually sends it — together they do what your browser’s address bar did in Part 1
httr2 resp_status(), resp_body_json() E → T (the handoff) resp_status() checks for 200, and resp_body_json() unwraps the JSON body into an R named list — the bridge from response to data
tibble tibble(), tribble() T Builds the rectangular data frame — the “something we can analyze” from the goal sentence
dplyr bind_rows() T Stacks many small tibbles into one big one (we’ll need this the moment we ask about more than one city)
purrr map(), pmap() T (the multiplier) Applies the same E+T recipe to many inputs — this is the “automation” that makes R better than the browser
ggplot2 ggplot() V Turns the tibble into a plot — Session 4’s job

Notice the shape of that table: E is entirely httr2, T is tibble + dplyr + purrr, and V is ggplot2. When an error message mentions a function, the library it came from tells you which ETV step broke — that’s your debugging compass for the rest of the workshop.

Tip🎯 Goal Check

ETV is the goal sentence, written as three letters: E = make a request, T = format the response, V = analyze it. And the libraries are the goal sentence written as code: httr2 makes the request, tibble/dplyr/purrr format the response, ggplot2 analyzes it.

Extract — The Browser Request, Now in R

Let’s have R do exactly what the browser just did. This block is pre-built — run it as-is, then read it top to bottom:

# E is for Extract ------------------------------------------

# Step 1: Start from the endpoint and add the query
req <- request("https://api.open-meteo.com/v1/forecast") |>
  req_url_query(
    latitude = 35.28,
    longitude = -120.66,
    current = "temperature_2m",
    temperature_unit = "fahrenheit"
  )

# Step 2: Look at the URL R built for us — same as the browser one!
req

# Step 3: Send the request
response <- req_perform(req)

# Step 4: Check the status code
resp_status(response)

The status should be 200 — success, just like Session 1 taught us to expect.

Notereq_url_query() Writes the URL for You

Each argument becomes one key=value pair in the query string, and httr2 handles the ?, the &, and any special-character encoding automatically. Printing req shows the finished URL — compare it character-by-character with the one you pasted into your browser.

# Step 5: Parse the JSON body into a named list
result <- resp_body_json(response)

# Step 6: Peek at the structure
str(result, max.level = 2)

Scaling Up: Many Cities with map()

What if we want several cities? We don’t need to copy-paste the code three times, and we don’t need to write our own function either. We give pmap() a recipe — an anonymous function, written \(...) — and it applies the recipe to every row of a small table.

This block is pre-built. Don’t type it — run it, watch it work, then read it with the note below. (In your workshop file, a few blanks mark the values you choose; everything structural is already written.)

# A small table of cities and their coordinates
cities <- tribble(
  ~city,             ~latitude, ~longitude,
  "San Luis Obispo",     35.28,    -120.66,
  "Boston",              42.36,     -71.06,
  "Ames",                42.03,     -93.62
)

# The recipe: for one row (one city), do E and T, return a one-row tibble
current_df <- cities |>
  pmap(\(city, latitude, longitude) {

    # E: extract
    result <- request("https://api.open-meteo.com/v1/forecast") |>
      req_url_query(
        latitude = latitude,
        longitude = longitude,
        current = "temperature_2m",
        temperature_unit = "fahrenheit"
      ) |>
      req_perform() |>
      resp_body_json()

    # T: transform
    tibble(
      city   = city,
      time   = result$current$time,
      temp_f = result$current$temperature_2m
    )
  }) |>
  bind_rows()

current_df
NoteReading the map Pattern
  • \(city, latitude, longitude) { ... } is an anonymous function — a recipe with no name. The \( ) lists the ingredients; the { } holds the steps.
  • pmap() runs the recipe once per row of cities.
  • Each run returns a one-row tibble; bind_rows() stacks them into one data frame.

Same ETV steps as before — just repeated for us, without copy-paste and without defining named functions. (Writing this recipe as a named function yourself is a great take-home exercise.)

Part 4: Geocoding + Your Turn

We typed the latitude and longitude by hand. But Open-Meteo also has a geocoding endpoint that converts a city name into coordinates.

Look First — A Different Door

Important⚠️ Look Closely — This Is a Different Endpoint

Compare the two front doors:

  • Forecast: https://api.open-meteo.com/v1/forecast
  • Geocoding: https://geocoding-api.open-meteo.com/v1/search

Everything changed — different subdomain (geocoding-api vs. api), different path (/search vs. /forecast), and it will take different query parameters (name and count instead of latitude and longitude). Remember Part 1: each service gets its own machine door. Different endpoint = different service = different inputs and different response shape. Reading an endpoint’s requirements is a skill you’ll use with every API you ever touch.

Browser first, as always — and this time let’s use Boston as our example. Paste this:

https://geocoding-api.open-meteo.com/v1/search?name=Boston&count=1

Now in Words

You’ll see JSON with a results array whose first entry contains Boston’s latitude (about 42.36), longitude (about -71.06), population, and more. We asked a name question at a different door and got a coordinates answer — same request/response loop, brand-new service. Now the same thing in R — pre-built again, with map() and an anonymous function:

city_names <- c("Boston", "San Luis Obispo", "Ames")

coords_df <- city_names |>
  map(\(nm) {

    # E: extract
    result <- request("https://geocoding-api.open-meteo.com/v1/search") |>
      req_url_query(name = nm, count = 1) |>
      req_perform() |>
      resp_body_json()

    # T: transform (first hit in the results array)
    hit <- result$results[[1]]
    tibble(
      city      = nm,
      latitude  = round(hit$latitude, 2),
      longitude = round(hit$longitude, 2)
    )
  }) |>
  bind_rows()

coords_df

Now we can find any city’s coordinates — which Session 4 will need, because the historical weather endpoint only speaks latitude/longitude (and Boston is one of the two cities Session 4 compares).

Tip🎯 Goal Check

Notice we just ran the same ETV pattern a third time — on a completely different endpoint, with different parameters and a different response shape — and none of our skills changed. That’s the whole trick: every API interaction, at every endpoint, at every company, is the same cycle.

## What About API Keys, Clients & Secrets?

## Part 2: The ETV Cycle + Extract in R

### Look First — The Map for the Rest of the Workshop

<!-- TODO(Immanuel): link/embed your ETV Cycle 4 notes here -->

Everything we do from here on follows one repeating cycle — **ETV**:

| Step | Name | What it means | In code |
|------|------|----------------|---------|
| **E** | **Extract** | Make the request, receive the JSON response | `request()` → `req_url_query()` → `req_perform()` |
| **T** | **Transform** | Format the response into a data frame | `resp_body_json()` → `tibble()` |
| **V** | **Visualize** | Turn the data frame into a plot | `ggplot()` |

### Now in Words

We'll do **E** and **T** in this session and add **V** in Session 4. Whenever you feel lost in code, ask: *which ETV step am I on right now?*

### Load Libraries

Each library we load is hired for **one specific ETV job**. Read the comments as a map of the whole workshop:

```{r}
#| output: false
library(httr2)       # E: makes web requests
library(tibble)      # T: tidyverse data frames
library(dplyr)       # T: data manipulation
library(purrr)       # T: map() — apply a recipe to many inputs
library(ggplot2)     # V: visualizations
```

### The Functions Behind Each Letter

Here's the deeper look — the specific functions each library gives us, and exactly where they sit in the cycle:

| Library | Key functions | ETV step | What it actually does |
|---------|---------------|----------|------------------------|
| `httr2` | `request()`, `req_url_query()`, `req_perform()` | **E** | `request()` starts from the endpoint, `req_url_query()` builds the query string (the part after `?`), and `req_perform()` actually sends it — together they do what your browser's address bar did in Part 1 |
| `httr2` | `resp_status()`, `resp_body_json()` | **E → T** (the handoff) | `resp_status()` checks for `200`, and `resp_body_json()` unwraps the JSON body into an R named list — the bridge from *response* to *data* |
| `tibble` | `tibble()`, `tribble()` | **T** | Builds the rectangular data frame — the "something we can analyze" from the goal sentence |
| `dplyr` | `bind_rows()` | **T** | Stacks many small tibbles into one big one (we'll need this the moment we ask about more than one city) |
| `purrr` | `map()`, `pmap()` | **T** (the multiplier) | Applies the same E+T recipe to many inputs — this is the "automation" that makes R better than the browser |
| `ggplot2` | `ggplot()` | **V** | Turns the tibble into a plot — Session 4's job |

Notice the shape of that table: **E is entirely `httr2`**, **T is `tibble` + `dplyr` + `purrr`**, and **V is `ggplot2`**. When an error message mentions a function, the library it came from tells you *which ETV step broke* — that's your debugging compass for the rest of the workshop.

::: {.callout-tip}
## 🎯 Goal Check
ETV *is* the goal sentence, written as three letters: **E** = make a request, **T** = format the response, **V** = analyze it. And the libraries are the goal sentence written as code: `httr2` makes the request, `tibble`/`dplyr`/`purrr` format the response, `ggplot2` analyzes it.
:::

### Extract — The Browser Request, Now in R

Let's have R do exactly what the browser just did. This block is **pre-built — run it as-is**, then read it top to bottom:

```{r}
# E is for Extract ------------------------------------------

req <- request("https://api.open-meteo.com/v1/forecast") |>
  req_url_query(
    latitude = 35.28,
    longitude = -120.66,
    current = "temperature_2m",
    temperature_unit = "fahrenheit"
  )

# Step 2: Look at the URL R built for us — same as the browser one!

# Step 3: Send the request

# Step 4: Check the status code
```

The status should be `200` — success, just like Session 1 taught us to expect.

### Scaling Up: Many Cities with `map()`

What if we want **several cities**? We don't need to copy-paste the code three times, and we don't need to write our own function either. We give `pmap()` a *recipe* — an **anonymous function**, written `\(...)` — and it applies the recipe to every row of a small table.

**This block is pre-built.** Don't type it — **run it, watch it work, then read it** with the note below. (In your workshop file, a few blanks mark the values you choose; everything structural is already written.)

```{r}
# A small table of cities and their coordinates
cities <- tribble(
  ~city,             ~latitude, ~longitude,
  "San Luis Obispo",     35.28,    -120.66,
  "Boston",              42.36,     -71.06,
  "Ames",                42.03,     -93.62
)

# The recipe: for one row (one city), do E and T, return a one-row tibble
current_df <- cities |>
  pmap(\(city, latitude, longitude) {

    # E: extract
    result <- request("https://api.open-meteo.com/v1/forecast") |>
      req_url_query(
        latitude = latitude,
        longitude = longitude,
        current = "temperature_2m",
        temperature_unit = "fahrenheit"
      ) |>
      req_perform() |>
      resp_body_json()

    # T: transform
    tibble(
      city   = city,
      time   = result$current$time,
      temp_f = result$current$temperature_2m
    )
  }) |>
  bind_rows()

current_df
```

::: {.callout-note}
## Reading the `map` Pattern

- `\(city, latitude, longitude) { ... }` is an **anonymous function** — a recipe with no name. The `\( )` lists the ingredients; the `{ }` holds the steps.
- `pmap()` runs the recipe once **per row** of `cities`.
- Each run returns a one-row tibble; `bind_rows()` stacks them into one data frame.

Same ETV steps as before — just repeated for us, without copy-paste and without defining named functions. (Writing this recipe as a named function yourself is a great [take-home exercise](take_home_exercises.qmd).)
:::

## Part 4: Geocoding + Your Turn

We typed the latitude and longitude by hand. But Open-Meteo also has a **geocoding** endpoint that converts a city *name* into coordinates.

### Look First — A Different Door

::: {.callout-important}
## ⚠️ Look Closely — This Is a *Different Endpoint*

Compare the two front doors:

- Forecast: `https://api.open-meteo.com/v1/forecast`
- Geocoding: `https://geocoding-api.open-meteo.com/v1/search`

**Everything changed** — different subdomain (`geocoding-api` vs. `api`), different path (`/search` vs. `/forecast`), and it will take different query parameters (`name` and `count` instead of `latitude` and `longitude`). Remember Part 1: each service gets its own machine door. Different endpoint = different service = different inputs and different response shape. Reading an endpoint's requirements is a skill you'll use with *every* API you ever touch.
:::

Browser first, as always — and this time let's use **Boston** as our example. Paste this:

```
https://geocoding-api.open-meteo.com/v1/search?name=Boston&count=1
```

### Now in Words

You'll see JSON with a `results` array whose first entry contains Boston's `latitude` (about 42.36), `longitude` (about -71.06), `population`, and more. We asked a *name* question at a *different door* and got a *coordinates* answer — same request/response loop, brand-new service. Now the same thing in R — **pre-built again**, with `map()` and an anonymous function:

```{r}
city_names <- c("Boston", "San Luis Obispo", "Ames")

coords_df <- city_names |>
  map(\(nm) {

    # E: extract
    result <- request("https://geocoding-api.open-meteo.com/v1/search") |>
      req_url_query(name = nm, count = 1) |>
      req_perform() |>
      resp_body_json()

    # T: transform (first hit in the results array)
    hit <- result$results[[1]]
    tibble(
      city      = nm,
      latitude  = round(hit$latitude, 2),
      longitude = round(hit$longitude, 2)
    )
  }) |>
  bind_rows()

coords_df
```

Now we can find *any* city's coordinates — which Session 4 will need, because the historical weather endpoint only speaks latitude/longitude (and Boston is one of the two cities Session 4 compares).

::: {.callout-tip}
## 🎯 Goal Check
Notice we just ran the **same ETV pattern a third time** — on a **completely different endpoint**, with different parameters and a different response shape — and none of our skills changed. That's the whole trick: every API interaction, at every endpoint, at every company, is the same cycle.
:::
