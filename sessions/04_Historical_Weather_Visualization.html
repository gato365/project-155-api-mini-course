Part 1: Historical Weather — The Full ETV Pipeline

Look First

Open-Meteo has yet another endpoint for past weather — the archive endpoint. Browser first, as always. Paste this — it asks for San Luis Obispo’s daily high and low temperatures for one week in July 2025:

https://archive-api.open-meteo.com/v1/archive?latitude=35.28&longitude=-120.66&start_date=2025-07-01&end_date=2025-07-07&daily=temperature_2m_max,temperature_2m_min&temperature_unit=fahrenheit&timezone=auto

You’ll see a JSON body whose daily object holds three parallel arrays — dates, daily highs, daily lows.

Now in Words

The endpoint is https://archive-api.open-meteo.com/v1/archive — a third door, following the same convention as Session 3’s forecast and geocoding doors. Two new query parameters do the date work: start_date and end_date. And here’s the good news — one request returns the entire date range. No loops needed.

Now the full pipeline in R, pre-built: geocode the city name → request the historical data → build the data frame. In your workshop file, the only blanks are the city name and the two dates — everything structural is written for you:

# Step 0 — Geocode: city name → coordinates (Session 3's endpoint)
city_name <- "San Luis Obispo"

geo <- request("https://geocoding-api.open-meteo.com/v1/search") |>
  req_url_query(name = city_name, count = 1) |>
  req_perform() |>
  resp_body_json()

hit <- geo$results[[1]]
my_lat <- round(hit$latitude, 2)
my_lon <- round(hit$longitude, 2)

# E: extract — historical request ---------------------------
result <- request("https://archive-api.open-meteo.com/v1/archive") |>
  req_url_query(
    latitude = my_lat,
    longitude = my_lon,
    start_date = "2025-07-01",
    end_date = "2025-07-07",
    daily = "temperature_2m_max,temperature_2m_min",
    temperature_unit = "fahrenheit",
    timezone = "auto"
  ) |>
  req_perform() |>
  resp_body_json()

# Peek at the daily piece
str(result$daily, max.level = 1)

The daily element is a named list of three parallel lists: time, temperature_2m_max, and temperature_2m_min — one entry per day.

# T: transform ------------------------------------------------
slo_df <- tibble(
  city     = city_name,
  date     = as.Date(unlist(result$daily$time)),
  temp_max = unlist(result$daily$temperature_2m_max),
  temp_min = unlist(result$daily$temperature_2m_min)
)

slo_df
NoteWhy unlist()?

resp_body_json() parses each JSON array into an R list. unlist() flattens that list into a plain vector, which is what a tibble column needs. List in, vector out — that’s all it does.

Part 2: Visualize — The V in ETV

Look First

We have a tidy data frame. Time for V — run this pre-built plot (in your workshop file, the blanks are the two column names being plotted):

# V: visualize -------------------------------------------------
ggplot(slo_df, aes(x = date)) +
  geom_line(aes(y = temp_max, color = "High"), linewidth = 1.2) +
  geom_line(aes(y = temp_min, color = "Low"), linewidth = 1.2) +
  scale_color_manual(values = c("High" = "red", "Low" = "blue")) +
  labs(
    title = "Daily High and Low Temperatures in San Luis Obispo",
    subtitle = "July 1–7, 2025 (Open-Meteo archive)",
    x = "Date",
    y = "Temperature (°F)",
    color = "Temperature"
  ) +
  theme_minimal(base_size = 14)

Now in Words

Each geom_line() pulls one column from the tibble: temp_max becomes the red “High” line, temp_min the blue “Low” line, and date runs along the x-axis. Change a column name and the plot changes with it — the plot is just the data frame, drawn.

🎉 That’s the entire workshop goal, end to end: we made a request, formatted the response, and analyzed it with a plot. Everything from here is variations on this cycle.

Q7.

(Discussion): You just built a complete data pipeline: API request → JSON parsing → data wrangling → visualization. Think about the courses you teach. Where could API data naturally integrate into your curriculum? What topics could benefit from live, real-world data?

TipExample Answers

Possible integration points:

  • Intro Stats: Use weather data for descriptive statistics (mean temperature, variability across cities)
  • Regression: Model temperature as a function of latitude or time
  • Data Wrangling: Parse nested JSON, clean and reshape API responses
  • Probability: Explore weather prediction accuracy (forecast vs. actual)
  • Capstone Projects: Let students choose an API and build their own data pipeline

———————

Common Pitfalls When Working with APIs

  1. Rate Limits: Most APIs limit how many requests you can make per minute/hour (Open-Meteo’s free tier allows ~10,000 calls/day — generous, but not infinite). Design your code to respect limits.

  2. API Keys (elsewhere): Most commercial APIs require keys. When you use one, never write the key directly in your script — store it in an environment file. The Practice Labs on this site walk through this.

  3. Data Structure Changes: API providers can change their response format without warning. Always inspect the structure of new responses (str()) before building pipelines around them.

  4. URL Encoding: Special characters (spaces, ampersands, accents) must be encoded in URLs. req_url_query() handles this for you automatically — one more reason to like it.

  5. Nested JSON Complexity: Real-world JSON can be deeply nested. Practice with str() and names() to navigate the structure before trying to flatten it.

### Common Pitfalls When Working with APIs

1. **Rate Limits:** Most APIs limit how many requests you can make per minute/hour (Open-Meteo's free tier allows ~10,000 calls/day — generous, but not infinite). Design your code to respect limits.

2. **API Keys (elsewhere):** Most commercial APIs require keys. When you use one, never write the key directly in your script — store it in an environment file. The Practice Labs on this site walk through this.

3. **Data Structure Changes:** API providers can change their response format without warning. Always inspect the structure of new responses (`str()`) before building pipelines around them.

4. **URL Encoding:** Special characters (spaces, ampersands, accents) must be encoded in URLs. `req_url_query()` handles this for you automatically — one more reason to like it.

5. **Nested JSON Complexity:** Real-world JSON can be deeply nested. Practice with `str()` and `names()` to navigate the structure before trying to flatten it.
