Part 1: Extract — Historical Weather Data

Open-Meteo has a second endpoint for past weather — the archive endpoint:

https://archive-api.open-meteo.com/v1/archive

Browser first, as always. Paste this — it asks for San Luis Obispo’s daily high and low temperatures for one week in July 2025:

https://archive-api.open-meteo.com/v1/archive?latitude=35.28&longitude=-120.66&start_date=2025-07-01&end_date=2025-07-07&daily=temperature_2m_max,temperature_2m_min&temperature_unit=fahrenheit&timezone=auto

Two new query parameters do the date work: start_date and end_date. And here’s the good news — one request returns the entire date range. No loops needed.

Now in R:

# E: extract -------------------------------------------------
result <- request("https://archive-api.open-meteo.com/v1/archive") |>
  req_url_query(
    latitude = 35.28,
    longitude = -120.66,
    start_date = "2025-07-01",
    end_date = "2025-07-07",
    daily = "temperature_2m_max,temperature_2m_min",
    temperature_unit = "fahrenheit",
    timezone = "auto"
  ) |>
  req_perform() |>
  resp_body_json()

# Peek at the daily piece
str(result$daily, max.level = 1)

The daily element is a named list of three parallel lists: time, temperature_2m_max, and temperature_2m_min — one entry per day.

# T: transform ------------------------------------------------
slo_df <- tibble(
  city     = "San Luis Obispo",
  date     = as.Date(unlist(result$daily$time)),
  temp_max = unlist(result$daily$temperature_2m_max),
  temp_min = unlist(result$daily$temperature_2m_min)
)

slo_df
NoteWhy unlist()?

resp_body_json() parses each JSON array into an R list. unlist() flattens that list into a plain vector, which is what a tibble column needs. List in, vector out — that’s all it does.

Part 3: Boston vs. San Luis Obispo — Two Simple Comparisons

Let’s use the map() pattern from Session 3 to compare two cities. The recipe below fetches one city’s daily highs for any date range:

cities <- tribble(
  ~city,             ~latitude, ~longitude,
  "San Luis Obispo",     35.28,    -120.66,
  "Boston",              42.36,     -71.06
)

Comparison 1: Summer

# E + T for both cities: July 2025
summer_df <- cities |>
  pmap(\(city, latitude, longitude) {

    result <- request("https://archive-api.open-meteo.com/v1/archive") |>
      req_url_query(
        latitude = latitude,
        longitude = longitude,
        start_date = "2025-07-01",
        end_date = "2025-07-31",
        daily = "temperature_2m_max",
        temperature_unit = "fahrenheit",
        timezone = "auto"
      ) |>
      req_perform() |>
      resp_body_json()

    tibble(
      city     = city,
      date     = as.Date(unlist(result$daily$time)),
      temp_max = unlist(result$daily$temperature_2m_max)
    )
  }) |>
  bind_rows()

# V: one line per city
ggplot(summer_df, aes(x = date, y = temp_max, color = city)) +
  geom_line(linewidth = 1.2) +
  labs(
    title = "Summer Daily Highs: Boston vs. San Luis Obispo",
    subtitle = "July 2025",
    x = "Date",
    y = "Daily High (°F)",
    color = "City"
  ) +
  theme_minimal(base_size = 14)

Part 5: Reflection & Pitfalls

Common Pitfalls When Working with APIs

  1. Rate Limits: Most APIs limit how many requests you can make per minute/hour (Open-Meteo’s free tier allows ~10,000 calls/day — generous, but not infinite). Design your code to respect limits.

  2. API Keys (elsewhere): Most commercial APIs require keys. When you use one, never write the key directly in your script — store it in an environment file. The Practice Labs on this site walk through this.

  3. Data Structure Changes: API providers can change their response format without warning. Always inspect the structure of new responses (str()) before building pipelines around them.

  4. URL Encoding: Special characters (spaces, ampersands, accents) must be encoded in URLs. req_url_query() handles this for you automatically — one more reason to like it.

  5. Nested JSON Complexity: Real-world JSON can be deeply nested. Practice with str() and names() to navigate the structure before trying to flatten it.

Reflection Questions for Your Practice

  • What are the pitfalls (rate limits, authentication) that students need to know?
  • How does working with live, messy data differ from working with pre-cleaned datasets?
  • What ethical considerations arise when collecting data from APIs?

## Part 5: Reflection & Pitfalls

### Common Pitfalls When Working with APIs

1. **Rate Limits:** Most APIs limit how many requests you can make per minute/hour (Open-Meteo's free tier allows ~10,000 calls/day — generous, but not infinite). Design your code to respect limits.

2. **API Keys (elsewhere):** Most commercial APIs require keys. When you use one, never write the key directly in your script — store it in an environment file. The Practice Labs on this site walk through this.

3. **Data Structure Changes:** API providers can change their response format without warning. Always inspect the structure of new responses (`str()`) before building pipelines around them.

4. **URL Encoding:** Special characters (spaces, ampersands, accents) must be encoded in URLs. `req_url_query()` handles this for you automatically — one more reason to like it.

5. **Nested JSON Complexity:** Real-world JSON can be deeply nested. Practice with `str()` and `names()` to navigate the structure before trying to flatten it.

- What are the pitfalls (rate limits, authentication) that students need to know?
- How does working with live, messy data differ from working with pre-cleaned datasets?
- What ethical considerations arise when collecting data from APIs?
