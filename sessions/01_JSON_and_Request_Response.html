Part 1: What is an API?

API stands for Application Programming Interface. At its core, an API is a way for software to communicate with other software. In data science, we use APIs to programmatically request data from external servers — weather services, sports databases, social media platforms, and more.

Now in Words

Here is the same story, written out:

  • You (the client) look at the menu and make a request — you place your order.
  • The waiter (the API) carries your request to the kitchen.
  • The kitchen (the server, with its fridge — the database) prepares your food.
  • The waiter brings back your meal (the response).

The key insight: you never walk into the kitchen yourself. The API is the controlled interface that lets you interact with the data source. And notice who starts everything: the client makes the request. Nothing happens until you order.

Now in Words

The animation traces a single API call from start to finish. There are four components in the chain: the Client (your R script or browser), the API (the endpoint — the “front door”), the Server (backend logic that processes the request), and the Database (where the actual data lives).

Request direction: Client (request) → API → Server → Database

Response direction: Client ← API ← Server (response) ← Database

NoteKey Observations
  • The client is your R script or browser — anything making the request.
  • The API is the endpoint — the “front door” of the data service.
  • The server processes the request and queries the database.
  • The response travels back the same path.
  • A client and server can exist on the same computer — this is common in local development.

Part 3: A Quick Detour — What is JSON?

Before we talk about what comes back from an API, we need a ten-minute detour. The responses we’ll be reading for the rest of this workshop are written in a format called JSON — so let’s meet it on its own first, before it shows up inside a response.

NoteWhy the Detour?

In the restaurant, the kitchen doesn’t hand you food in a random pile — every dish arrives plated in a predictable way. Data works the same way: servers send information back in one standard written format so that any program can read it. That format is JSON. Ten minutes here makes everything that follows easier.

What is JSON?

JSON stands for JavaScript Object Notation. Don’t let the name scare you — you do not need to know JavaScript. JSON is just plain text, written with a few simple punctuation rules, used to describe structured data.

APIs almost universally speak JSON because it is:

  • Human-readable — you can open it and read it with your eyes
  • Machine-readable — every programming language (including R) can parse it
  • Language-independent — a Python server can send it and your R script can read it
  • Lightweight — it’s just text, so it travels fast
ImportantJSON is a Format, Not the API

Keep these two ideas separate: the API is the waiter — the messenger. JSON is the language the receipt is written in. When we say “the API returns JSON,” we mean: the messenger hands you a note, and the note is written in JSON.

Keys and Values

Here is a small, complete JSON example — a single breakfast order:

{
  "dish": "veggie omelet",
  "price": 12.50,
  "gluten_free": true
}

Every entry follows the same pattern: "key": value.

  • The key is the label — always wrapped in double quotes: "dish"
  • The value is the information itself, and how it’s written depends on its type:
    • Strings (text) are in quotes: "veggie omelet"
    • Numbers are bare: 12.50
    • Booleans (true/false) are bare and lowercase: true
  • A colon : connects each key to its value; commas separate the pairs
  • Curly braces { } wrap the whole thing

Objects, Arrays, and Nesting

Three more words of vocabulary and you can read almost any JSON in the wild:

  • An object is anything wrapped in curly braces { } — a set of key-value pairs. The breakfast order above is one object.
  • An array is an ordered list, wrapped in square brackets [ ] — like ["egg", "cheese", "spinach"].
  • Nesting means an object (or array) sitting inside another object, as a value.

All three in one order:

{
  "table": 7,
  "customer": {
    "name": "Maya",
    "rewards_member": true
  },
  "items": ["pancakes", "omelet", "coffee"],
  "total": 31.25
}

Read it out loud: table 7; the customer is a nested object with a name and a membership flag; the items are an array of three dishes; the total is a number. That’s it — that’s JSON.

From the Café to the API

Now the payoff. Here is the same structure with different keys — this is the shape of a real weather API response:

{
  "city": "San Luis Obispo",
  "coordinates": {
    "lat": 35.28,
    "lon": -120.66
  },
  "weather": {
    "main": "Clear",
    "temp": 72,
    "humidity": 45
  }
}

Nothing here is new: one object with keys and values, two of which (coordinates and weather) are nested objects. If you could read the avocado toast, you can read this — and this is exactly what will arrive every time our R script calls the weather API tomorrow.

ImportantThinking in R Terms

In R, a JSON object becomes a named list, and a JSON array becomes a vector or list. Nested objects become lists inside lists. When we flatten it all with as.data.frame(), nested keys become column names like coordinates.lat or weather.temp.

Tip🎯 Goal Check

Half of our goal is “format the response into something we can analyze.” You just did the first step by eye: reading JSON and finding the values you care about. Tomorrow, R does the same thing — just faster.

Part 4: Requests and Responses

Now let’s zoom in on the two key actions: requests and responses. We’ll keep this simple — the details come in Session 2.

What is a Request?

A request is the client asking for information. Here is the one thing to remember today:

A request is written as a URL — a web address.

That’s it. When we want data from an API, we build a web address that describes what we want, and we send it. In Session 2 we will dissect exactly how that web address is put together, piece by piece.

(One aside for later: some APIs also ask you to include an ID called an API key — like showing a library card. The weather API we use in this workshop is free and doesn’t need one, so we can set that idea aside for now.)

What is a Response?

The server returns a response which contains:

  • Status code — tells you whether the request was successful (e.g., 200 OK)
  • Metadata — information about the response (timestamps, units, etc.)
  • Data — the actual information you requested (temperature, artist name, forecast, etc.)

This information is traditionally provided in JSON format — the format we just met in Part 3. In Part 5, we’ll see how a full response body is laid out.

Tip🎯 Goal Check

Two halves of our goal, side by side: the request is a URL we send; the response is what we’ll format into something we can analyze.

Part 6: Status Codes

Status codes tell you what happened with your request. They are grouped by category:

Range Category Meaning
1xx Informational Request received, processing…
2xx Success Request was successful
3xx Redirect Resource moved to a different URL
4xx Client Error Something wrong with your request
5xx Server Error Something wrong on the server’s end

The most important ones for data work:

  • 200 OK — Success! You got your data.
  • 401 Unauthorized — Your credentials (e.g., an API key) are missing or invalid.
  • 403 Forbidden — You don’t have permission to access this resource.
  • 404 Not Found — The endpoint or resource doesn’t exist.
  • 429 Too Many Requests — You’ve hit the rate limit.
  • 500 Internal Server Error — The server broke; not your fault.
NotePractical Tip

In most data API work, your goal is to get a 200 response. If you don’t, the status code tells you where to look for the problem — your request (4xx) or their server (5xx).

Tip🎯 Goal Check

The status code is the first thing we check after making a request: a 200 means “the response arrived — go ahead and format it for analysis.”

———————

Q11.

(Fill in the Blank): A status code in the 4xx range means the mistake is on the ________ side; a 5xx code means the problem is on the ________ side.

TipAnswer Q11

4xx = the client side (you — your URL or request has a problem). 5xx = the server side (them — their system broke).

## Part 3: A Quick Detour — What is JSON?

Before we talk about what comes back from an API, we need a ten-minute detour. The responses we'll be reading for the rest of this workshop are written in a format called **JSON** — so let's meet it on its own first, before it shows up inside a response.

::: callout-note
## Why the Detour?

In the restaurant, the kitchen doesn't hand you food in a random pile — every dish arrives plated in a predictable way. Data works the same way: servers send information back in one standard written format so that any program can read it. That format is JSON. Ten minutes here makes everything that follows easier.
:::

### What is JSON?

**JSON** stands for **JavaScript Object Notation**. Don't let the name scare you — you do not need to know JavaScript. JSON is just **plain text**, written with a few simple punctuation rules, used to describe structured data.

APIs almost universally speak JSON because it is:

-   **Human-readable** — you can open it and read it with your eyes
-   **Machine-readable** — every programming language (including R) can parse it
-   **Language-independent** — a Python server can send it and your R script can read it
-   **Lightweight** — it's just text, so it travels fast

::: callout-important
## JSON is a Format, Not the API

Keep these two ideas separate: the **API** is the waiter — the messenger. **JSON** is the language the receipt is written in. When we say "the API returns JSON," we mean: the messenger hands you a note, and the note is written in JSON.
:::

### Keys and Values

Here is a small, complete JSON example — a single breakfast order:

``` json
{
  "dish": "veggie omelet",
  "price": 12.50,
  "gluten_free": true
}
```

Every entry follows the same pattern: `"key": value`.

-   The **key** is the label — always wrapped in double quotes: `"dish"`
-   The **value** is the information itself, and how it's written depends on its type:
    -   **Strings** (text) are in quotes: `"veggie omelet"`
    -   **Numbers** are bare: `12.50`
    -   **Booleans** (true/false) are bare and lowercase: `true`
-   A colon `:` connects each key to its value; commas separate the pairs
-   Curly braces `{ }` wrap the whole thing

### Objects, Arrays, and Nesting

Three more words of vocabulary and you can read almost any JSON in the wild:

-   An **object** is anything wrapped in curly braces `{ }` — a set of key-value pairs. The breakfast order above is one object.
-   An **array** is an ordered list, wrapped in square brackets `[ ]` — like `["egg", "cheese", "spinach"]`.
-   **Nesting** means an object (or array) sitting *inside* another object, as a value.

All three in one order:

``` json
{
  "table": 7,
  "customer": {
    "name": "Maya",
    "rewards_member": true
  },
  "items": ["pancakes", "omelet", "coffee"],
  "total": 31.25
}
```

Read it out loud: table 7; the customer is a nested object with a name and a membership flag; the items are an array of three dishes; the total is a number. That's it — that's JSON.

## Part 4: Requests and Responses

Now let's zoom in on the two key actions: **requests** and **responses**. We'll keep this simple — the details come in Session 2.

### What is a Request?

A request is the client *asking* for information. Here is the one thing to remember today:

> **A request is written as a URL — a web address.**

That's it. When we want data from an API, we build a web address that describes what we want, and we send it. In Session 2 we will dissect exactly how that web address is put together, piece by piece.

*(One aside for later: some APIs also ask you to include an ID called an **API key** — like showing a library card. The weather API we use in this workshop is free and doesn't need one, so we can set that idea aside for now.)*

### What is a Response?

The server returns a **response** which contains:

-   **Status code** — tells you whether the request was successful (e.g., `200 OK`)
-   **Metadata** — information *about* the response (timestamps, units, etc.)
-   **Data** — the actual information you requested (temperature, artist name, forecast, etc.)



This information is traditionally provided in **JSON format** — the format we just met in Part 3. In Part 5, we'll see how a full response body is laid out.

::: callout-tip
## 🎯 Goal Check

Two halves of our goal, side by side: the **request** is a URL we send; the **response** is what we'll format into something we can analyze.
:::

## Part 6: Status Codes

Status codes tell you what happened with your request. They are grouped by category:

| Range   | Category      | Meaning                               |
|---------|---------------|---------------------------------------|
| **1xx** | Informational | Request received, processing...       |
| **2xx** | Success       | Request was successful                |
| **3xx** | Redirect      | Resource moved to a different URL     |
| **4xx** | Client Error  | Something wrong with *your* request   |
| **5xx** | Server Error  | Something wrong on the *server's* end |

**The most important ones for data work:**

-   **200 OK** — Success! You got your data.
-   **401 Unauthorized** — Your credentials (e.g., an API key) are missing or invalid.
-   **403 Forbidden** — You don't have permission to access this resource.
-   **404 Not Found** — The endpoint or resource doesn't exist.
-   **429 Too Many Requests** — You've hit the rate limit.
-   **500 Internal Server Error** — The server broke; not your fault.

::: callout-note
## Practical Tip

In most data API work, your goal is to get a **200** response. If you don't, the status code tells you *where* to look for the problem — your request (4xx) or their server (5xx).
:::

::: callout-tip
## 🎯 Goal Check

The status code is the first thing we check after making a request: a **200** means "the response arrived — go ahead and format it for analysis."
:::
